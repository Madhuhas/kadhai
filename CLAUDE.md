# CLAUDE.md

Guidance for Claude Code when working in this repository.

## What this is

Kadhai: a local, zero-cost multi-agent coding workspace. A Node/Express server orchestrates six LLM agents named after a kitchen brigade (plus user-defined custom agents) over free-tier APIs with automatic failover, and serves a vanilla-JS dashboard. It is also an MCP server, an MCP client and an ACP agent. See [README.md](README.md) for the overview, [docs/USER-GUIDE.md](docs/USER-GUIDE.md) for the user-facing description and [docs/DEVELOPERS.md](docs/DEVELOPERS.md) for a readable developer overview (this file stays the complete list of rules).

## Commands

```bash
npm install          # one dependency: express
npm start            # dashboard on http://localhost:4747 (needs keys in .env)
npm run demo         # same, with simulated providers - use this to try UI changes
npm run dev          # start with node --watch
npm test             # node:test suite, offline, ~15 s (needs git on PATH for the checkpoint test)
npm run mcp          # MCP server on stdio
npm run acp          # ACP agent on stdio
node --check <file>  # quick syntax check; there is no linter or build step
```

Run a single test: `node --test --test-name-pattern="dispatcher" test/core.test.js`. Tests live in `test/core.test.js`, `test/features.test.js`, `test/hardening.test.js` (security and robustness regressions) `test/flame.test.js` (the flame and skill import), `test/runs.test.js` (around a run: tokens, failure lessons, circuit breaker, security pass), `test/agents.test.js` (high flame: CLI agents against `test/fixtures/fake-agent.mjs`, parallel steps, file recall) and `test/flows.test.js` (flow data and expressions, every node type, credentials, sub-flows, pins, run history, polled starts, test steps, OpenAPI import); a new test file must be added to the `test` script in `package.json`.

## Hard constraints

These are product requirements, not preferences. Do not trade them away.

- **Zero cost to run, low footprint.** Target machine: 7th-gen i7, 12 GB RAM, no GPU. Kadhai must stay fully usable with free keys only: nothing may *require* a paid service. Paid keys and subscriptions are things the user may bring (they asked for both); they are opt-in, labelled as paid, and guarded by a daily token limit. No local model inference by Kadhai itself, no heavy runtime dependencies. Adding an npm dependency needs a strong reason; `express` is currently the only one.
- **No frontend build step or framework.** `public/` is hand-written ES modules, served as-is. No web fonts or CDN assets — the UI must work offline.
- **ESM only**, Node >= 20, built-ins imported with the `node:` prefix.
- **Local only.** The server binds to loopback only (`127.0.0.1`, plus `::1` so that `localhost` works from Node clients) and `localOnly` in [src/http/app.js](src/http/app.js) rejects non-loopback Host/Origin headers. Keep both.
- **The desktop app is opt-in and lives apart.** The user chose a real packaged app (Electron, 2026-10-23) knowing it is heavy. It stays in [desktop/](desktop/README.md) with its own package.json, so `npm start` never downloads Electron and the main package keeps `express` as its only dependency - never move Electron (or anything it needs) into the root package.json. [desktop/main.cjs](desktop/main.cjs) only gives the server a window: it runs `server.js` with Electron's Node.js (`ELECTRON_RUN_AS_NODE`, `KADHAI_DESKTOP=1`: the server then shuts down when its stdin closes, like a room), or uses a Kadhai already answering on the port. Behaviour belongs in `src/`, as for every shell. Keep its guards: the window loads only `http://localhost:<port>`, anything else goes to `shell.openExternal` (http and https only) or nowhere, `contextIsolation` + `sandbox` and no Node.js in the page, every permission refused but the clipboard. Packaged, the user's files go in the app's data folder through **`KADHAI_DATA`** (`DATA` in config.js: keys, settings, agents, flows, triggers, credentials, mcp.config.json, skills.local, rooms.local, .env and the default workspace); code (built-in skills, public, LICENSE) is read from `ROOT`. A new user-owned file must be built from `DATA`, never `ROOT`. `server.js` deletes `ELECTRON_RUN_AS_NODE` so commands never inherit it, and `Rooms` adds it back for its children when it runs inside Electron.
- **stdout is a protocol channel** in `bin/mcp-server.js` and `bin/acp-agent.js`. Never `console.log` in `src/`; use `log` from [src/core/util.js](src/core/util.js), which writes to stderr.

## Architecture

`createEngine()` in [src/core/engine.js](src/core/engine.js) builds one fully wired engine for one workspace folder, for life. The HTTP server, the MCP server and the ACP agent are thin shells around it — put behaviour in `src/core`, not in a shell.

**Rooms** (shown to the user as **kitchens** since 2026-10-19, at their request: every visible "room" in the UI, the docs and the server's messages says kitchen; the code, routes, files and folders keep `room`). More than one folder at once is done with *processes*, not with several engines in one: [src/http/rooms.js](src/http/rooms.js) starts `node server.js --room <id>` as a child on its own pair of ports (`PORT + 10·k`), with `rooms.local/<id>.json` as that room's settings file and `<id>.agents/.flows/.triggers.json` as its own crew, flows and triggers. The first server is the only one that manages rooms (`Rooms`); a room reaches that list through `RoomsProxy` (server-to-server over loopback - the browser never talks across ports, which `localOnly` and the CSP forbid). A room exits when its stdin closes, i.e. when the first server goes. Do not replace this with multiple engines behind one router: every route, the event stream, the preview origin and the dispatcher's accounting assume one engine per process, and process isolation is what makes "both busy at once" safe. **One folder, one room**: `Host` marks its folder with `.kadhai/room.lock` (pid and port) and refuses to open one held by another live process; keep that check in `Host.open` and `Rooms.open`. Shared between rooms are only root-level files read by every process (keys, skills, MCP settings); `watchKeys` makes each engine re-read the key file when another process changes it.

The web server does not hold an engine directly: it holds a `Host` ([src/http/host.js](src/http/host.js)). Opening another folder in the dashboard builds a new engine and swaps it in; the host rebuilds the per-engine API router, MCP endpoint and preview files, ends the old engine's event streams (dashboards reconnect and re-sync) and closes it. So never capture `engine` at app level in `src/http` — go through `host`. Routes that outlive an engine (`/api/workspace/*`) live in `workspaceRouter(host)`.

```
EventBus ── every state change is published here; SSE, ACP and memory.md subscribe
LockManager ── cross-process file mutex (lock files under <workspace>/.kadhai/locks)
Workspace ── the only code that touches workspace files
MemoryEngine ── owns memory.md
Dispatcher ── route table + failover; calls providers.chatCompletion; setProviders() swaps routes live
Keys ── keyStore.js (keys.local.json) + keys.js (add/remove/verify, model lists) for the dashboard
Crew ── the six house agents + custom ones: state/metrics/streams; crew.call() is the single path to an LLM
Orchestrator ── the hub: plan -> sub-tasks -> review -> fix
Runner ── shell commands in the workspace: approval, timeout, process-tree kill, optional Docker sandbox
Checkpoints ── shadow git repo in .kadhai/git: snapshot before/after each run, diff, restore
StateStore ── .kadhai/state.json: chat, run list, daily usage (only when config.persist)
Repo ── git.js: source control on the workspace's OWN repository (status, stage, commit, branches, push/pull)
Vault ── vault.js: AES-256-GCM for every secret on disk; vaultFor(file) gives the vault of that file's folder
Anthropic ── anthropic.js: the Claude Messages API spoken natively (raw fetch: the one-dependency rule outweighs the SDK here)
CliProvider ── cliProvider.js: subscription CLIs as model routes (kind 'cli'); complete() picks CLI or HTTP per route
CliAgent ── cliAgent.js: high flame only - a subscription CLI as an agent with its own tools, in a temp copy of the folder (AGENT_MODES, canAct, runCliAgent)
Journal ── journal.js: .kadhai/journal.jsonl (one line per run with a plan) + .kadhai/lessons.json; search/describe for the Chef, lessonsFor(agent) for prompts
Flows ── flows.js: a graph of nodes + wires, validated as loop-free and run in wire order, JSON travelling along the wires (flowData.js: {{ expressions }}, conditions); an agent node is one orchestrator.start with a pinned cook and the apps plugged into it; run history in <flowsFile>.runs.json; flowDraft.js: "describe a flow" (the Chef draws one from plain words)
Services ── services.js: built-in service nodes (SERVICES), polled starts (POLLERS), CREDENTIAL_TYPES, the one `request()` helper; catalog() is what the browser sees (no functions)
Credentials ── credentials.js: credentials.local.json, vault-encrypted, shared by every room (re-read when the file changes); list() never carries a secret
Triggers ── triggers.js: webhook + GitHub/Linear/Telegram polling; each calls orchestrator.start like a typed task
GoogleConnector ── connectors/google.js: OAuth sign-in with the user's own client, read-only tools; Toolbox merges them with MCP tools for the cooks
McpHub ── client for external MCP servers (tools for the cooks); add/remove/restart at runtime, persisted to mcp.config.json
```

### The flame

Low flame (the default) and high flame are two sets of bounds, not two sets of models: any key works on either. [src/core/flame.js](src/core/flame.js) holds them. `createEngine` keeps the configured limits as low flame (env and test overrides apply there) and `engine.setFlame(level)` writes the chosen set into `config.limits`, which everything reads when it acts, so a change applies from the next model call; `flame:update` tells the UI. High flame never lowers a configured number. It raises sub-tasks, review and tool rounds, answer length, file context, skills, lessons, journal look-ups and tools per sub-task, turns on `cliAgents` (invariant 14), `parallelCooks` 3 (steps side by side, see *Invariants* 1) and `fileRecall` (invariant 5), and sets `strongFirst`: `Dispatcher.#pick` then walks paid and subscription routes before free ones (a `prefer`red model still comes first, failover still applies, the paid daily token limit still holds). Every number on either flame is a hard bound; adding a new token-saving cap means giving it a low and a high value there. The flame belongs to the host, not the engine: the first room keeps it in `settings.local.json` for every room, a room may keep its own in its room file (`null` = follow the first room, which it watches like the key file), it survives a folder switch, and the dashboard reaches it through `/api/workspace/flame`.

### The crew

`ROSTER` in [src/core/crew.js](src/core/crew.js) defines the six house agents: `general-manager` (role `manager`; shown to the user simply as "Chef" - the id keeps its old name because locks, saved history and tests use it), `commis` / `chef-de-partie` / `executive-chef` / `sous-chef` (role `coder`), `head-chef` (role `reviewer`). **`role` is the job, `id` is who holds it.** Prompts, the mock provider and test fakes key off `role`; locks, command ownership, metrics and the UI key off `id`.

Cook selection is code, not model choice: `COOK_FOR_LEVEL` maps the plan's `level` to a cook, fixes go to `FIX_COOK`, and a failed sub-task is retried once by `ESCALATION_COOK`. `tier: 'light'` (Prep) makes the dispatcher walk the route table from the bottom.

**Custom agents** (`crew.hire/retrain/dismiss`, saved to `agents.local.json` via `engine.hiring`; **Generate with AI** in the hire form is `hiring.generate` / `POST /api/crew/generate`: one Chef call ([src/core/agentDraft.js](src/core/agentDraft.js)) that returns form values only - `shapeAgentDraft` keeps names unique, skills to ids in the library and instructions within the 1500 the form keeps; refused while a run is busy; nothing is hired until the user presses Hire) are always `role: 'coder'`. Their one-line speciality goes into the Chef's prompt (`crew.specialists()`), which may set `"cook": "<id>"` on a sub-task; `#sanitizePlan` honours it only if that id exists, otherwise it falls back to `COOK_FOR_LEVEL`. Their instructions are appended to the coder system prompt *after* the output protocol, so they cannot redefine it. The roster is deliberately small: every agent must do distinct work, and the user asked for no decorative roles.

**Switching agents off** (`off: true` in the same settings; the user asked: "not every time we need all agents"). The Chef can never be switched off and one cook always stays on (`Crew.configure` refuses both). Work meant for a cook that is off goes to `crew.cookFor(id)`: the nearest house cook that is on, up `COOK_LINE` first, then down, then a hired one - `#sanitizePlan`, escalation and the fix step all ask it, so a fix step is marked `fix: true` rather than recognised by `FIX_COOK`. A Taster that is off means no review and no security pass (the verify command still runs: no model call), reported as "skipped". A specialist that is off is left out of `crew.specialists()`, so the Chef is never told about it. This only ever removes calls - keep it that way. In the browser: the switch in each crew-list row (`crew-line`), **Switch off** on the agent tab, `shownState` 'off', a faded station.

**Agent settings** (`crew.configure(id, { hue, model, skills, connections, off })`, `PUT /api/crew/:id/settings`, saved through `engine.hiring.configure` as a `settings` map in `agents.local.json`) apply to *any* agent, house or hired. `hue` is the user's colour (null = the usual one; the browser's `hueOf` reads it from `state.agents`). `model` is `''` (the agent's own order), `'best'`, `'light'`, or `'<provider>/<model>'`: `Crew.call` passes the last as `prefer` to `Dispatcher.#pick`, which tries it first *only while it is usable* - failover to the normal order must stay. `skills` are ids from the library: built-in ones in `skills/*.md` (or `skills/<id>/SKILL.md`) and the user's own in `skills.local/` (git-ignored, marked `own`), merged by `loadSkills(dir, ownDir)` and listed in the snapshot as `skills` without bodies. `engine.skills.save/remove` (`POST/PUT/DELETE /api/skills`) write the user's own and call `crew.setLibrary`, so a new or edited skill is used on the next call with no restart; built-in ones are read-only, and deleting a skill takes it off every agent that had it. Up to `MAX_SKILLS_CHOSEN` (5) may be chosen; the flame decides how many reach a prompt and how much of each (`skillsPerAgent` / `skillChars`: 3 and 900 on low flame, 5 and 3000 on high), clipped by `skillsBlock` in `prompts.js` at a line end and appended to the system prompt *after* the output protocol in `Crew.call`. Do not raise the low-flame numbers casually: the free tiers allow about 8k tokens a minute. `POST /api/skills/import` (`skillImport.js`) fetches a skill from an https link (GitHub page links become raw files), and if it is longer than high flame carries, condenses it in one call through the Chef (`condenseSystem`): most important rules first, so low flame's cut still works. It returns a draft for the form; nothing is saved until the user saves it. `connections` is `null` (every connection, the default) or a list of connection ids (the group ids of `Toolbox.groups()`; `[]` means none): `crew.mayUse(id, connection)` is asked twice in the orchestrator, when a sub-task's tools are put in the cook's prompt and again before every tool call in `#fulfil`. Keep the second check - a model can name a tool it was never shown. Ids that are not connected right now are kept, not dropped. `GET /api/connections` lists what is connected for the edit dialog. The same question is also asked from the connection's side: `crew.restrict(connection, [agentIds] | null)` (`PUT /api/connections/:id/access`, saved as an `access` map in `agents.local.json`, sent in the snapshot as `access`) keeps a connection for certain cooks. `mayUse` requires both to agree. Fail closed: dismissing an agent leaves its connections reserved for nobody rather than opening them to everyone; only removing the MCP server (the `DELETE /mcp-servers/:name` route) clears a reservation. The UI for it is `accessPanel` in `public/js/mcp.js`.

### Invariants

1. **Hub and spoke.** All hand-offs go through `Orchestrator` (plan → sub-tasks → verify → review → fix). Adding an agent must not add model calls to a run: it takes over an existing call (as custom cooks do). One run at a time; inside a run, `#schedule` cooks up to `limits.parallelCooks` steps at once (1 on low flame: in order, exactly as before) - a step starts when the steps it `needs` are finished (always earlier ones; a step the Chef said nothing about needs the one before it), its cook is free (`#asCook`: one step per cook, escalations included) and no step at work shares a declared file; a step sent by level moves to a free cook of the same grade or above (`#freeCook`), a pinned cook or specialist never does. A fault (abort, providers out) waits for the steps already at work before it ends the run; extra tasks wait in `orchestrator.queue`, and `run.done` always resolves (never rejects), queued or not - `#recover` covers a fault while wrapping a run up, so the queue can never be left stuck. Agents never call or prompt each other, and control flow is code, not model output. Every loop that calls an LLM has a hard bound from `config.limits`. On top of those bounds the **circuit breaker** (`BREAKER` in the orchestrator) only ever removes calls: a step with mistakes in two rounds running is narrowed (whole files only, look-ups and commands not served), after three it stops, and a run with two failed steps marks the rest `skipped`. A request already answered in the step (a read, a tool call, or a command with nothing written since it ran) is not served again and counts as a mistake. The one bounded addition is high flame's **security pass** (`limits.securityReview`): a change whose paths or contents match `SENSITIVE` gets one `#review(..., { focus: 'security' })` call and at most one fix. Waiting tasks start in the order they arrived (`#advance`); the board that let one wait for another was removed at the user's request (2026-10-15) - do not bring back task-to-task dependencies without asking.
2. **All file access goes through `Workspace`.** It enforces the sandbox (`resolve`), symlink checks, the mutex and atomic writes. Never call `fs` on workspace paths elsewhere. Protected names are compared the way the disk reads them, not as typed: any letter case, and on Windows no trailing dot or space and no `:` (`.GIT`, `.git.` and `MEMORY.MD` are the real thing there). Ask `workspace.isMemory(rel)` rather than comparing with `MEMORY_FILE`.
3. **Every write holds the file's lock.** `Workspace.writeFile/deleteFile` acquire it themselves; the orchestrator additionally holds a sub-task's declared files for the whole sub-task. Locks are re-entrant per owner string, and `handle.release()` must run in a `finally`.
4. **`memory.md` has exactly three sections** (Current Objective, Active File Locks, Last Completed Milestone) and is written only by `MemoryEngine` (`system: true`). Do not add sections or let agents write it — its small size is the token-saving mechanism.
5. **Agents are stateless.** No chat history is ever sent. Prompts are `memory.md` + the files a step needs + at most `LESSONS_IN_PROMPT` lines / `LESSON_PROMPT_CHARS` characters of lessons (`journal.lessonsFor(agent)`: the agent's own first, then the project's). That cap is the whole design: the journal may grow to 500 runs and the lessons to 40, and a prompt still gets the same small, fixed amount (high flame's amount is bigger, and just as fixed - see *The flame*). Never put journal entries into a prompt except through the Chef's `need_history` look-up (one extra call, bounded like `need_files`, result capped by `HISTORY_CHARS`) and high flame's `journal.recallFiles` (one line per earlier run that touched the step's files, within `limits.fileRecall` characters, 0 on low flame, no model call), and never raise the caps to "give the agents more memory". Lessons come from the review that already runs (the Taster's optional `lessons`, and its issues attributed to the cook of that file) and from a failed run's own record (the failed step's summary for its cook, a failed check for the folder; never from `PROVIDER_ERRORS` or a stopped run) - never from an extra model call. Prompts are still built by functions in [src/core/prompts.js](src/core/prompts.js) and re-evaluated on every provider attempt (`req.build`) so a hot-swapped model sees current state.
6. **Provider errors are classified, not string-matched downstream.** `providers.js` throws `ProviderError` with a `kind` (decided in one place per dialect: `classify(status, body)` for OpenAI-style servers, which reads the body of a 400 because providers disagree on status codes; `classifyAnthropic` for Claude; `classifyCli` for subscription CLIs); `Dispatcher.#penalize` maps `kind` to cooldown/disable/skip. New failure handling goes in those two places.
7. **API keys never leave the server.** `Dispatcher.#view` is the public shape of a route; do not add `key` to it or to any event. The keys API is write-only: responses carry `maskKey()` and `keyId()` only, and keys must never be logged. `Runner` strips key-like variables from child-process environments.
8. **Every command goes through `Runner.run`.** Never `spawn`/`exec` a model- or client-supplied command elsewhere. The one exception is a high-flame CLI agent the operator allowed commands for one task (invariant 14): its own shell runs in its temp copy, outside Runner. `keep: true` (a dev server: no time limit, `exec:port` when it prints a local address) is for `trusted` commands only, capped by `limits.keepRunning`, refused in the Docker sandbox, and still stopped by `kill`/`killAll` - a crew run must never be able to leave a process behind. `onPath` (the terminal's red "not installed") only looks at PATH folders; it must never run the name it is given. Agent and MCP commands are untrusted (`trusted: false`): they pass the blocklist and, in `ask` mode, wait for approval. Only commands the operator typed in the dashboard are `trusted`. Default mode stays `ask`; execution is not sandboxed, so do not describe it as safe.
9. **Sandbox failures fail closed.** With `EXEC_SANDBOX=docker`, an unreachable Docker makes `Runner.check` throw. Never add a fallback to host execution.
10. **Two gits, never mixed.** `git.js` (`Repo`) drives the user's own repository for the Source control panel; `checkpoints.js` drives a private shadow repository for undo. `Repo` must never add commits on its own, and every path it gives git goes through `Workspace.resolve` and after `--`. Operations that rewrite the working tree (`discard`, `checkout`, `pull`) are refused while a run is busy. **Checkpoints use only the shadow repo.** Every git call goes through `Checkpoints.#git`, which pins `--git-dir` to `.kadhai/git`. Never run git against the workspace's own `.git` (in ACP mode the workspace is the user's real project). Checkpoint failures are logged and the run continues without one. The shadow repo may have arrived with a folder someone else made, so `Checkpoints` rewrites its config on every start, points `core.hooksPath` at nothing, and only lets commit ids (`COMMIT_ID`) reach `diff`/`restore`. Keep all three.
11. **A failed edit writes nothing.** `applyEdits` is all-or-nothing per file; a missed hunk, or any text in an EDIT block that is not a complete hunk (`edit.stray`), goes back to the cook as a problem to correct, bounded by `maxToolRounds`. Never apply the well-formed part of a malformed edit: a real model produced exactly that, and the dropped half was the point of the task. A hunk with an empty SEARCH appends to the file. Tolerance is for *spelling*, never for *content*: the parser accepts what real models get slightly wrong (two or four closing brackets on a marker, a REPLACE marker up to twelve `>` long, a tool written as `name()`, the same tool call twice, an opener with no `>>>` at all when its line holds a lone path (`<<<FILE login.js`), a RUN whose `>>>` is on the next line by itself, and a last block with no `<<<END>>>` **only when the provider reported the answer as finished** - `parseWorkerOutput(..., { complete })`, false when `finishReason` is `length`). An answer cut off at the output limit is still half a file and is never saved. The other way round, a FILE block whose first or last line still carries a piece of a marker (a lone `>>>`, or `>>>` glued to its last line: `strayMarker`) is refused and sent back, never saved - a real model's login.test.js was saved with a `>>>` line and could not load (2026-10-22). Each of these came from an actual answer of a Groq model; when a real model trips the parser in a new way, add its exact text to `test/hardening.test.js` before loosening anything.
12. **Stop a child with `killTree`** (in `util.js`), never `child.kill()`: on Windows anything launched through a shell is a grandchild, and killing the shell leaves it running.
13. **Secrets are encrypted before they touch the disk.** Anything secret that is saved (a key, a token, an MCP server's `env` value, a flow credential) goes through `vaultFor(file).encrypt` on write and `.decrypt` on read; `decrypt` passes plain text through, so hand-edited files keep working. `encrypt` throws rather than write plain text. Do not describe this as more than it is (see *Safety and privacy* in docs/USER-GUIDE.md): on Windows the master key is DPAPI-wrapped, elsewhere it is a 0600 file.
14. **A subscription CLI is a model; on high flame it may be an agent, but never in the workspace.** `cliCompletion` starts it for one answer with its tools off, in an empty temp folder, prompt on stdin (or a temp file), `childEnv` for its environment. Nothing a model or a file wrote may go into its command line. On high flame (`limits.cliAgents`) `Orchestrator#subtaskAgent` lets one do a whole step with its own tools: `Checkpoints.exportTo` writes a fresh checkpoint into a temp folder with an index of its own (no `.git`, no `memory.md`), `runCliAgent` runs it there (`--setting-sources user --strict-mcp-config` for Claude Code, so nothing the folder brought runs; `agentTurns`, `agentTimeoutMs` bound it), and `changesIn` + `#takeBack` bring each change into the workspace through `Workspace` under the cook's name - a file changed here meanwhile is merged with `git merge-file`, a conflict is refused, binaries and `memory.md` are never copied back. Never point a CLI at the workspace itself: that would bypass `Workspace` and the locks. **Edits only** unless the operator ticked *agents run commands* for that task in the dashboard (`start(..., { shell })`, honoured only for `source: 'ui'`): without it only a CLI whose `AGENT_MODES` entry is `editsOnly` (it can switch its shell off) may act (`canAct`). With it the CLI's commands bypass `Runner` and its approval - that is the operator's explicit, per-task choice; never make it a default or reachable from flows, triggers, MCP or ACP, and never describe it as sandboxed. When no CLI can act, or the chosen one fails with a `ProviderError` (`Crew.act` returns null and the dispatcher cools it down via `fault`), the ordinary cook does the step. Its failures are classified in one place, `classifyCli`, into the same `kind`s the dispatcher already understands, plus `unavailable` (not installed / not signed in -> route disabled with the message).
15. **Nothing calls in.** Triggers poll outward (GitHub, Linear, Telegram); the webhook route sits behind `localOnly` like everything else. Do not exempt it from the Host check or add a tunnel. Every trigger has a gate (token, label, chat list) and whatever arrives is an ordinary untrusted task: it goes through `orchestrator.start`, never straight to an agent or to `Runner`.
16. **A flow may branch but never loop, and its agent nodes are ordinary runs.** `Flows.#clean` refuses a drawing whose wires form a cycle; `#execute` runs each node at most once, in wire order, and only nodes something was delivered to. An **agent** node is `orchestrator.start(text, { source: 'flow', cook, tools })` - the pins are applied in `#sanitizePlan` (the Chef still plans; `pin.cook` replaces its choice of cook, `pin.tools`, taken from the app nodes wired into the agent's tools port, its choice of connections; `crew.mayUse` still has the last word). `Flows` reaches a model only through `start` (agent nodes) and `crew.call` (AI nodes: one bounded call, at most `limits.flowAiTokens` long - 2000 on low flame, 8000 on high), and runs commands only through `Runner.run`. An **app** node calls `toolbox.call` directly, with no model and no approval, because the operator chose that exact action; text from the flow is put into its JSON with `jsonEscape`, so it can only ever be a string value, and an http node's address takes no templates at all. Keep the bounds (`MAX_AGENT_NODES` - agent and AI nodes together -, `MAX_NODES`, `MIN_INTERVAL_MINUTES`, `MAX_DEPTH` for flows that run flows, `MAX_WAIT_SECONDS`, `RUNS_KEPT`) and keep it loop-free: agent nodes are model calls made with nobody watching. `#checkCalls` refuses flows that would reach themselves again through flow nodes or an "if it fails" flow, and `#execute` checks the chain again at run time. Retries (`NO_RETRY`) are never offered on nodes that call a model, need an approval or run another flow. The scheduler never catches up missed runs and counts the next one from now. A flow saved as a list of steps (the first version) is converted by `fromSteps` on load.

    **What text from outside may reach.** Expressions (`flowData.js`) are paths - `input`, `trigger`, `node('Name')`, `now`, `today` and `.field` / `[0]` - never code, and an expression that cannot be read is refused when saving. Some settings are **fixed** and take no `{{ }}` at all: an HTTP address and its headers, a command, a file name, and every service field marked `fixed` (repositories, recipients, topics, ids). Into JSON (app args, HTTP JSON bodies) text goes through `jsonEscape`; query parameters are URL-encoded by `URLSearchParams`. Keep each of these when adding a node or a service field. **Polled starts** (`POLLERS`, and `'app'`) only ask outward; the first look only notes what is there (`cursor.primed`), at most `POLL_BATCH` new items start runs per look, and they queue (`#queues`, at most `QUEUE_MAX`) rather than run side by side. A **file** start ignores every change made while any flow runs and for `FILE_QUIET_MS` after, and waits `FILE_GAP_MS` between its own starts - otherwise a flow that writes a file (or an agent node that does) would start itself for ever. The **code** node runs in `codeNode.js`: a worker thread, a fresh `vm` context holding only the data, 5 s and 64 MB, terminated afterwards. That contains a mistake, not hostile code; the code comes only from the operator in the dashboard, so never let a model, a trigger or an import write it silently (an import opens as an unsaved draft for the user to look at). File nodes go through `Workspace` (owner `flow:<id>`); command nodes through `Runner.run`, untrusted, so they wait for approval in `ask` mode. Pinned data is used only for runs started by hand (`runNow(id, { pins })`) and test steps, never by schedules or triggers. `testNode` runs one node of an unsaved drawing; it does the real thing, which is why the browser asks before testing an agent, AI, command or flow node.

    **Try once** (`flows.tryOnce`, `POST /api/flows/try`) runs a drawing, saved or not, with `#execute(..., { dry: true })`: nodes that only read or think run for real (service actions marked `reads` in `services.js`, GET requests, file reads, AI nodes, logic), and `#held` stands in for everything else - other service actions, other HTTP methods, file writes, commands, agent, app and flow nodes, and waits - handing on what it *would* have done with the data filled in. The start gets what `#sampleStart` would deliver now. Nothing is saved and nothing goes into the history; the record comes back to the canvas as a run with `source: 'try'`. A service action is held back unless it is listed in `READS`: keep that default, so a new action that sends something can never be fired by a try. App nodes are always held back (a tool's effect is unknown).

    **Change it / Fix it** use the same `flows.draft(text, { base, failure, id })`: `base` is the drawing on the canvas (checked with `#clean` first), `failure` the failed node, its error and input. The model is shown the flow with no credential ids and no code (`baseForPrompt`) and answers with the whole flow; `mergeWithBase` then puts back by node id what only the user sets - credentials (same service), pinned data, off, retries, carry-on-error, positions, a code node's code - and places new nodes beside what feeds them; `diffFlows` compares the *checked* result with the base, so only real changes are marked and listed. The browser swaps the drawing in as one undo step, unsaved.

    **Describe a flow** (`flows.draft`, `POST /api/flows/draft`, [src/core/flowDraft.js](src/core/flowDraft.js)) lets the Chef draw a flow from plain words: one `crew.call` (`json`, `maxTokens` 4000), and more only if the answer fails `#clean` / `#checkCalls` or quotes a `node('Name')` that does not run before it (`badReferences`), told why - at most `limits.draftCalls` calls in all (2 on low flame, 3 on high), with the services and tools listed up to `limits.draftCatalogChars`. Refused while a run is busy. It never saves or runs anything: the browser opens the result as an unsaved draft. What only the operator may choose is taken away in code (`shapeDraft`), not by the prompt: credentials are cleared, a **code** node becomes a sticky note, `{{ }}` in a fixed field (and in a URL, path or command) is emptied, and positions come from `layout`, not the model. The canvas also shows every flow **in words** (`explain` in `public/js/flows.js`), worked out from the drawing with no model: the start, then each step in run order, with where it comes from when that is not the step before, and how many model calls a run makes. `attention` marks each node to check (`node.check`, shown as `[!] check`; `#clean` drops it on save): a credential to choose, an empty required field, a fixed value the user's request did not contain, an address, a command, a file written. The prompt tells the model what every service and start hands on (`GIVES`): keep it in step with the `run` functions in `services.js` (a test checks every action has an entry). Real Groq runs found each of these: double-escaped `\n`, ids as names (`format_line`), ai prompts that quoted no `{{ input }}`, parallel wires where a chain was meant, a GitHub start told `"release"` (silently read as issues), and a command with `failOnError` that ended the flow before its alert.
17. **Generated pages are untrusted.** The preview is served from a second port so it is a different origin, and `localOnly` rejects any Origin that is not the dashboard's own. Do not serve workspace files from the dashboard origin. The dashboard is sent with a Content-Security-Policy (`CONTENT_POLICY` in `app.js`) that allows only this server's own script files: never add an inline `<script>` or an `onclick=""` attribute to `index.html` (a test checks), and load nothing from another host. The preview adds one script to the folder's HTML pages (`PAGE_ERRORS_SCRIPT` in `host.js`) that only `postMessage`s errors to its parent; `browser.js` accepts them only from the frame's window and the preview origin, and **Fix this** turns them into an ordinary `api.task` (untrusted text, like anything typed in the chat). The one thing it frames is the browser tab ([public/js/browser.js](public/js/browser.js)): `frame-src` names loopback only (a test checks), the address bar refuses anything else and the dashboard's own port, and the frame is sandboxed without `allow-top-navigation`.
18. **A sub-task that names files must write one.** `#sanitizePlan` marks such a sub-task `mustWrite`; a cook that answers it with words only is told so and given another round, and if it still writes nothing the sub-task has failed (and is escalated), however confident its summary. Without this a run reported success having done nothing - seen with a real model. A sub-task with no files (look something up, run something) may finish on a summary. A step that wrote only *new* files, none of them the ones it was given, is told so once (a real Prep wrote `src/calc.js` for `calc.js` and the next step's import failed); editing an existing file at another path is a fair correction of the plan and is accepted. Cooks are told to READ any workspace file whose code they describe, import or call (a real docs writer invented functions it had never seen). The run report says "fixed by the Fixer" only when the Fixer's round changed a file (`fixResult`); otherwise it says the Fixer changed nothing and repeats what the Taster found. Two more things a real reasoning model did, both handled in `#subtask`: it asked for a tool with `<<<READ tool_name>>>`, and it left its request in its *thinking* with only a summary in the answer - when an answer asks for and does nothing, look-ups (TOOL, READ) found in `out.reasoning` are honoured, never a FILE, EDIT, DELETE or RUN.

### Model output formats

- The Chef and the Taster return one JSON object (parsed with the tolerant `extractJson`). The plan may carry `verify`: one single-line command the orchestrator runs before the review. A fix sub-task is told that command and may run it, and gets every file the run changed (the issues' files first). `managerSystem` is told the runner's shell, and on `cmd.exe` to check with `node -e` rather than `test`/`grep` (a real model planned Unix checks for Windows; they passed only because Git's tools happened to be on PATH).
- The cook returns plain-text blocks, not JSON, because escaping code inside JSON breaks weaker models: `<<<FILE path>>> … <<<END>>>`, `<<<EDIT path>>>` with `<<<<<<< SEARCH / ======= / >>>>>>> REPLACE` hunks then `<<<END>>>`, `<<<DELETE path>>>`, `<<<READ path>>>`, `<<<RUN command>>>`, `<<<TOOL name>>>{json}<<<END>>>`, `SUMMARY: …`. Parser: `parseWorkerOutput` in [src/core/parse.js](src/core/parse.js). If you change the format, change the prompt, the parser, `mockProvider.js` and the parser test together.

### Frontend

The screen is a small desktop: a taskbar (brand, rooms, the crew as a drop-down list plus a button for each agent that is busy, providers, terminal, flows, connect, keys, the flame, and a **more** menu with browser, about and theme) and three windows under it: files (left), the stage (middle: a `kitchen.exe` tab that is always there, plus one tab per agent you have opened and one tab for an open file or diff), chat (right). `files.js` owns the tree, the stage tabs, the file viewer and the folder dialog; `crew.js` owns the crew bar, the kitchen floor and the single agent panel all agent tabs share (it asks for a tab with the `agenttab` event, and `files.js` tells it which agent is in front with `agentshow`); `console.js` owns the chat; `usage.js` the usage bar along the bottom (live from `providers:update`, which the dispatcher sends after every call; at most `SHOWN` (3) model chips - in use, rate-limited or used today - and one "+N more" that opens the providers list, because a row per model ran off the screen with 15 models); `browser.js` owns the browser tab (`browsertab` opens it, with an address or none; `files.js` shows the tab). `layout.js` owns the window layout: the taskbar's lock pill (`.lock-icon`, a padlock drawn in CSS with two boxes - the user asked for a lock icon; its shackle lifts when unlocked; locked = the default grid; locking puts everything back), the drag edges on the files and chat windows (`.win-edge`, `role="separator"` with arrow keys; widths as `--files-w` / `--chat-w`, only above 860px, the stage never under `MIN.stage`) and full screen for files, stage, chat and flows (`[]` buttons `.win-max`, a title-bar double-click, `Esc`; `#app[data-max]`). It is a per-browser preference (`prefs` key `layout`), never sent to the server. The stage's tabs sit in `.stage-head` beside its `[]` button. The taskbar's `.top-actions` wraps to a second line rather than push the page sideways. Its tools (models, terminal, flows, connect) and settings (keys, flame, lock, more) are split by a thin `.bar-gap`; the providers pill shows only the model in use (or "models"), and the flame is shown in the taskbar only, not in the usage bar - each fact once (2026-10-23 design pass). **Send** is the one solid button in the main view; Commit is outlined. [public/js/store.js](public/js/store.js) holds `state` and a tiny `on/emit` bus. `app.js` turns SSE events into state changes and topics (`sync`, `agents`, `thought`, `providers`, `locks`, `fs`, `run`, `runs`, `chat`, `exec`, `execmode`, `showdiff`, `showpatch`, `git`, `floor`, `resync`, `agenttab`, `agentshow`); the modules (`crew.js`, `files.js`, `console.js`, `settings.js`) render on those topics. Build DOM with `h()` from `util.js` and set text via `textContent` — the only `innerHTML` uses are `mdLite`, `highlight` and `renderDiff`, each of which escapes the text before adding markup (keep it that way: file contents and diffs are model-written).

**The look is specified in [theme.md](theme.md)** (copied from the user's Sai project, at their request) — read it before changing any UI. A surface is a window (2px border, hard `--shadow`, a `.panel-head` title bar) or a card (1px `--line` border); code-like things (thought stream, command cards) sit on the dark `--term-*` surface. Nine themes, registered in `THEMES` in `settings.js`, each a variable set in `themes.css`: `light` (default, the Sai look), `modern` ("Normal light", VS Code Light Modern), `solarized`, `dark` (VS Code Dark Modern), `dracula`, `nord`, `cyberpunk`, `amber` (CRT) and `contrast`. ## Common tasks

- **Add a subscription CLI:** add it to `CLI_AGENTS` in [src/core/cliProvider.js](src/core/cliProvider.js): the fixed `args`, `input: 'split'` if it takes the system prompt separately, a `read` if its output is not plain text, `checked` saying how far you verified it, and `terms` (one line on what the vendor's own terms say about a plan used from another tool, the page it comes from, `risky: true` if they warn against it - the keys dialog shows it and asks before switching a risky one on). Take the flags from the vendor's CLI reference or `--help`, never from memory, and make sure the flags switch its tools off. To let it work as a high-flame agent, add it to `AGENT_MODES` in [src/core/cliAgent.js](src/core/cliAgent.js) with `args` (its streaming JSON output, writes kept to its folder), `events` (one JSON line -> `text` / `tool` / `result` / `error`), and `editsOnly: true` only if a documented flag really removes its shell.
- **Add a built-in service** (a flow node, no MCP): add it to `SERVICES` in [src/core/services.js](src/core/services.js) - `label`, `auth` (a key of `CREDENTIAL_TYPES`, plus `authOptional` / per-action `needsAuth`), `checked`, and actions with `fields` (mark addresses, recipients, ids and repositories `fixed`) and `run({ p, cred, fetch, signal })` built on `request()`. Probe the endpoint with a wrong key first and record the result in `checked` (`used` only after a real call from this code); take endpoints from the vendor's current docs, never from memory (Todoist's REST v2 already answers 410). A new credential kind goes in `CREDENTIAL_TYPES` with a `verify` if one cheap authenticated GET exists. A new polled start goes in `POLLERS` and returns `[{ key, data }]`. The browser draws everything from `catalog()`; a logo is optional (`public/logos/<id>.svg`).
- **Add a trigger type:** add it to `TRIGGER_TYPES` (fields, `clean`, `checked`) and a poller to `#pollers` in [src/core/triggers.js](src/core/triggers.js). A poller returns `[{ key, text, reply? }]`; `key` is what makes an item fire once. Probe the endpoint first (a bad token must be rejected), start from "now" rather than replaying a backlog, and give it a gate.
- **Paid providers** are presets with `paid: true` (and `api: 'anthropic'` for Claude, which goes through `anthropicCompletion`). Rules: `models: []` unless the ids come from an authoritative current source (a paid `/models` cannot be listed without a key, and ids must never come from memory); probe the endpoint with a bogus key first; give it a `prefix` only if the key format is unmistakable (`detectProvider`). Paid routes carry `paid` into the dispatcher, which holds them to `paidBudget` (tokens a day, all paid routes together, checked in `#pick` via `#overBudget`); with nothing else to fall back on the run ends with `DispatchError('BUDGET')`. Kadhai knows no prices: never show money, only tokens. For Claude: do not send `temperature` or a `thinking` block (current models reject one or the other), keep `max_tokens` at 16000 or more (thinking shares it), and treat `stop_reason: "refusal"` as `bad_request` so the next route is tried. `chatCompletion` learns per route (`route.quirks`) when a server wants `max_completion_tokens` or no `temperature`.
- **Endpoints of the user's own** (`keys.addEndpoint`, ids start `own-`) are stored in `keys.local.json` under `endpoints` and appear in `providerCatalog` like presets. `https` only, except this computer, which is also keyless and not paid.
- **Add a provider:** add a preset to `PROVIDER_PRESETS` in [src/config.js](src/config.js): OpenAI-compatible `baseUrl`, `keyUrl`, `freeTier`, `models` (may be empty), `extra: true`, and the right `verifyUrl`. Before adding one, probe it: `GET {baseUrl}/models` with a bogus key. If that returns 401 the default check works; if it returns 200 the list is public and proves nothing, so set `verifyUrl` to an endpoint that does need auth, or `false` if there is none. Take default model ids from the provider's live `/models`, never from memory or a third-party list. It then appears in the Keys dialog automatically.
- **Add a house agent:** add it to `ROSTER` in [src/core/crew.js](src/core/crew.js) with a `role`, and give it a place in the orchestrator's flow. The UI renders the roster dynamically. For a new *kind* of cook, prefer a custom agent - no code needed.
- **Connectors** (`src/core/connectors/`) expose `tools()` and `call(name, args)` exactly like `McpHub`, so `Toolbox` can offer everything to the cooks as one list; the orchestrator only ever sees the toolbox. Rules for any connector: request the narrowest (read-only) scopes, keep client secrets and tokens server-side (`status()` returns the email and nothing else sensitive), verify the OAuth `state` on callback, and take an injectable `fetch` so tests never touch the network. A new connector also needs its routes in `apiRouter` and a card in `public/js/mcp.js`.
- **The connector catalog** is [src/core/connectors/catalog.js](src/core/connectors/catalog.js); the dashboard gets it from `GET /api/catalog` (never the commands) and starts an entry with `POST /api/catalog/:id/connect`, which answers at once — progress arrives as `mcp:update`. An entry's `id` is its MCP server name, which is how the UI matches cards to servers. An entry that takes a key may name a credential type in `verify` (`checkFields`, run before anything starts): GitHub's token is checked this way, because with a refused token mcp-remote falls back to a browser sign-in. **Add an entry only after checking it** and record how far you got in `checked` (`used` / `starts` / `live`): confirm the npm package or address is real, then start it through `McpHub`. Do not add entries from memory, deprecated packages, or ones needing `uvx`/Docker.
- **Tools are scoped per sub-task.** `Toolbox.groups()` gives the Chef one line per connection (group = the tool-name prefix before `__`); the plan's `subtasks[].tools` names up to `limits.toolsPerSubtask` (3 on low flame, 5 on high); `toolsFor()` puts only those tools in that cook's prompt. Never go back to listing every tool in every prompt: one connector can bring thirty descriptions, and the free tiers allow about 8k tokens a minute.
- **MCP tool servers** are managed by `McpHub` (`add`, `remove`, `restart`, `setEnabled`) and surfaced by `public/js/mcp.js`. `status()` must never include env *values* (they hold tokens) — names only. It reads each server's stderr for the last log line (shown when a start fails) and for a sign-in address (`signInUrl`, shown as a fallback link). A saved server that asked for a sign-in and did not get one is marked `needsSignIn` in `mcp.config.json` and gets status `signin`: `loadConfig` does not start it again until the user presses **Sign in** (`restart`), and the mark is cleared once it connects. Keep that: `mcp-remote` opens the browser every time it starts without a sign-in and has no switch to stop it, so every Kadhai start opened a tab (seen with Canva). `splitCommand` deliberately does not treat backslashes as escapes, because Windows paths are full of them.
- **The terminal** ([public/js/terminal.js](public/js/terminal.js)), a non-modal panel opened from the taskbar and docked in the lower part of the stage (a flex child, not an overlay, so the kitchen above it still scrolls), is a view of the same `exec:*` events the chat cards use, plus a prompt. It is not a PTY and must not become a second way to run things: what you type goes to `POST /api/exec` and so through `Runner.run` (`trusted`, since the operator typed it). `cd` is handled in the browser (each command is its own process) and sent as `dir`, which the route resolves with `Workspace.resolve` so it cannot leave the workspace; `Runner.run({ dir })` starts the process there (or passes `-w` to the sandbox). No stdin: do not promise interactive programs.
- **Chat attachments** are ordinary workspace files: `POST /api/attach` saves each under `attachments/` (suffixing the name rather than overwriting), and `orchestrator.start(text, { attachments })` appends their paths to the request and puts their contents in the Chef's first prompt (`managerUser`'s `attached`). Nothing else changes: cooks still see only the files their sub-task lists.
- **Add an MCP tool:** append to `buildTools` in [src/protocols/mcpServer.js](src/protocols/mcpServer.js). It is then available over both stdio and `/mcp`.
- **Highlight another language:** add its extension to `EXTENSIONS` in [public/js/highlight.js](public/js/highlight.js), or a new rule list to `FAMILIES`. Patterns must not contain capturing groups.
- **A plan step has `cook` (the name to show) and `cookId` (who it is).** Colour by `cookId`; `tintOf(name)` gives a wrong hue.
- **Every form field needs a name**: a `<label>`, or `aria-label` / `ariaLabel` in `h()`. A placeholder alone is not one.
- **The flows canvas** ([public/js/flows.js](public/js/flows.js), with [public/js/flowKit.js](public/js/flowKit.js) for node kinds, the data viewer, the curl parser and the examples) keeps a `draft` (`{ name, description, tags, onFail, nodes, edges }`) that only Save sends; every change goes through `touch()`, and `commit()` turns a burst of them into one undo step. Nodes are absolutely placed in `.flow-space`, which is scaled by the zoom inside `.flow-sizer`; anything that turns a pointer position into canvas coordinates must divide by `zoom` (`toSpace`, `portPoint`). Wires are redrawn from the ports' real positions after every render and during a drag. Everything is pointer events, no library. A node's kind is the class `node-<type>` (plain `trigger` is already taken by the triggers list); sticky notes are `.sticky` (`.flow-note` is a paragraph style). Every mouse action has a keyboard twin (the *wire to…* picker and wire list in the settings, Tab for the node search, Delete, Ctrl+Z, arrows) - keep that when adding a node type, and add the type to `NODE_TYPES` and `#config` / `#runNode` in `src/core/flows.js`, `KINDS` (and `outPorts` if its ports differ) in `flowKit.js`, and `nodeForm` / `summary` in `flows.js`. Settings that take `{{ }}` are wrapped in `expr()` so a field clicked in the data viewer lands there. The large view (`#flow-ndv`) and the settings panel build the same forms; while it is open the panel shows nothing, so two inputs never edit one value.
- **Layout breakpoints:** three columns; under 860px the files column goes; under 620px the stage sits above the chat, menus open full width, and the taskbar keeps only kitchens, crew, the flame and **more**: terminal, keys, flows, connect, providers and the layout lock move into **more** as `.phone-only` entries whose `data-proxy` names the taskbar button they press (layout.js). A new taskbar button needs such an entry too. Check a new panel at 390px wide for sideways scroll.
- **A flow's agent node tells the Chef what it was given.** Connections pinned by a flow are passed to `managerUser` as `pinned` ("these are tools a cook calls, not files"). Without it the Chef planned as if they were not there, and a connection called `memory` was read as `memory.md`.
- **Never pass `false` or `null` to `replaceChildren()`:** the DOM prints them as text. Use `...(cond ? [node] : [])`. (`h()` filters falsy children; `replaceChildren` does not.)
- **The About panel** ([public/js/about.js](public/js/about.js)) shows `engine.about()` (`GET /api/about`): version, runtime, folders, counts, safety settings. When a feature adds something a user would want to see there (or in a bug report), add it to `about()` and to `sections()`. Never put a key, a token or an email in it - "Copy details" exists so the whole thing can be pasted into a message.
- **Add an HTTP route:** `apiRouter` in [src/http/app.js](src/http/app.js); wrap async handlers in `wrap()` so errors reach the error middleware (which maps `ELOCKED` to 423 and `err.status` otherwise).

## Verifying changes

- **Against real models** (do this after touching prompts, the parser or the orchestrator - the mock never makes a mistake): start a copy with `KADHAI_MCP=off PORT=4799 WORKSPACE_DIR=<a scratch folder> node server.js` (no `KADHAI_MOCK`; `KADHAI_MCP=off` keeps it from starting the user's MCP servers, which a sign-in one would answer by opening their browser), send tasks to `POST /api/task`, approve what appears in `state.exec.pending`, and read the agents' `thought` in `GET /api/state` when something goes wrong. It uses the real keys and shares the root's local files, so back up `mcp.config.json` first and remove what the copy created afterwards.
- Backend changes: `npm test`. Add a case to [test/core.test.js](test/core.test.js) for new core behaviour; tests use the mock provider and a temp workspace, never the network.
- UI changes: `npm run demo`, then send any task in the browser. The mock provider rate-limits every third call on route `alpha` and the mock cook asks to run `node --check`, so one run exercises planning, locks, hot-swaps, the command-approval card, review and the file tree.
- Protocol changes: pipe newline-delimited JSON-RPC into `node bin/mcp-server.js --mock` or `node bin/acp-agent.js --mock`.

## Gotchas

- **Two repositories since 2026-10-23:** this app is public at github.com/Madhuhas/kadhai; the website is private at github.com/Madhuhas/kadhai-website (a folder beside this one, `../kadhai-website`). The website keeps a copy of `public/js/ascii3d.js`: when the drawing changes here, copy it there. **No `Co-Authored-By` lines in commits** - the user does not want Claude listed as a contributor.

- **VS Code sets `ELECTRON_RUN_AS_NODE=1` in its terminals** (it is an Electron app). Started from there, any Electron binary runs as plain Node.js (`bad option: --remote-debugging-port`). `desktop/start.cjs` clears it for `npm start`; a test of the packaged app needs `env -u ELECTRON_RUN_AS_NODE`. Test the packaged app with `PORT=4799 KADHAI_DATA=<scratch> KADHAI_MCP=off` so it never touches the user's files or running app.
- The version is a pre-release (`1.0.0-beta.1`, user's choice 2026-10-23): the taskbar shows a BETA tag while it has `-alpha`, `-beta` or `-rc` (`renderPill` in settings.js), so dropping the suffix removes the tag. Keep `desktop/package.json`'s version in step.

- Windows is the primary platform. Lock keys are lower-cased there; renames are retried on `EPERM`/`EBUSY`; `.cmd` launchers (npx) are spawned through a shell in `mcpClient.js`.
- Persistence is opt-in (`persist: true` in `server.js` and the ACP agent). Tests and the stdio MCP server leave it off so they never write `state.json`.
- Daily usage rolls over at local midnight (`Dispatcher.#day`). `route.quota` is whatever rate-limit headers the provider last sent and may be null.
- Command approval needs an approver: the dashboard (`interactive: true`, set only in `server.js`) or ACP's `runner.approver`. Engines without one refuse `ask`-mode commands instead of hanging; tests set `limits.execMode` explicitly.
- Providers come from two merged sources: `.env` and `keys.local.json` (`providerCatalog`/`readProviders` in `config.js`). `config.providers` and `config.mock` are mutable at runtime — adding a key in the dashboard leaves demo mode and calls `dispatcher.setProviders`. Tests pass `keysFile` and `verifyKey` overrides so they never touch the real file or the network.
- Tests that assert on the roster pass an `agentsFile` override so they never see agents the user really hired.
- `settings.local.json` records the folder last opened in the dashboard; it wins over `WORKSPACE_DIR` at start-up. A test server started from this repo shares that file, so clean it up after driving the folder dialog.
- `skills/` ships with built-in skills and is also where the user adds their own; a test asserts every built-in fits in 900 characters. Tests that load skills pass a `skillsDir` override.
- **An engine built with the default files must never rewrite them.** Only the three entry points pass `sealSecrets: true` / `triggers: true`; a test gets them by naming a `keysFile` / `triggersFile` of its own. (A test run once encrypted the user's real key file because a start-up step wrote to the default path.)
- The vault's first use on Windows starts PowerShell once (DPAPI), about a second. It is lazy for that reason: do not touch the vault on a path every test takes.
- The journal exists where `config.journal` is true (it follows `persist`, so the dashboard and ACP have it; tests pass `journal: true` and an `overrides.now` clock). Entries are stamped with `journal.now()`, the same clock a question's "yesterday" is measured against.
- `rooms.local/` is user-owned and git-ignored: one small JSON per extra room, plus that room's agents, flows and triggers files. A throwaway copy for testing must be given its own `KADHAI_ROOMS_DIR`, or it would start (and could close) the user's real rooms.
- `skills.local/` is user-owned and git-ignored. Tests that write skills pass `ownSkillsDir` (and `skillsDir`) so they touch neither the user's skills nor the built-in folder.
- `credentials.local.json` (flow credentials, encrypted) and `flows.local.runs.json` (the run history) are user-owned and git-ignored. Tests pass `credentialsFile`; the history file follows `flowsFile`.
- `flows.local.json` is user-owned and git-ignored too; like triggers, flows exist only where `flows: true` (the dashboard server) or a test names a `flowsFile`. Tests drive the scheduler with `overrides.now` and `flows.tick()`, never with real time.
- `secret.local.key` and `triggers.local.json` are user-owned and git-ignored like the other local files. Deleting `secret.local.key` makes every saved secret unreadable.
- `workspace/`, `.env`, `keys.local.json`, `agents.local.json`, `settings.local.json`, `connectors.local.json` and `mcp.config.json` are git-ignored and user-owned. Do not commit or overwrite them.
- Default model IDs in `config.js` go stale as providers rotate their free line-ups. Check the providers' model pages before changing them rather than guessing.
